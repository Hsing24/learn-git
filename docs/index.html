🛠️ 現代 Git 指令演進：經典舊指令 vs. 現代更優實現

許多舊指令承擔過多職責或語意晦澀。現代 Git（2.23+）進行了大幅現代化升級，以下為業界最新推薦的寫法：

操作情境 傳統舊指令 現代更優替代指令 為什麼現代實現更好？
切換分支 git checkout <branch> git switch <branch> checkout 承擔切分支與復原檔案雙重職責，容易手滑覆蓋；switch 專門切分支，安全明確。
建立並切換新分支 git checkout -b <new> git switch -c <new> 語意更直觀對稱（-c 代表 create），降低認知負擔。
放棄工作區修改 git checkout -- <file> git restore <file> checkout -- 語法晦澀；restore 顧名思義就是還原，直覺不易打錯。
移出暫存區 (Unstage) git reset HEAD <file> git restore --staged <file> 不用搬出危險的 reset，restore --staged 精準描述取消暫存。
跨分支平行開發 (Hotfix) git stash ➜ 切換 ➜ pop git worktree add <dir> <branch> 實體目錄隔離，避免重編譯快取與 node_modules 失效，免除 pop 衝突風險。
新分支首次推送 git push -u origin <branch> push.autoSetupRemote true + git push 設定一次一勞永逸，任何新分支直接 git push，自動建立遠端同名分支。
微調修正歷史 Commit 手動 rebase -i 逐行改 squash git commit --fixup + --autosquash 自動將 fixup commit 移到目標下方自動合併，零手動編輯出錯風險。
拉取遠端最新代碼 git pull（預設 merge） git pull --rebase 避免產生雜亂無章的菱形交叉 Merge Commit，保持乾淨線性歷史。
二分法排查 Bug 手動一步步 good/bad git bisect run <test_script> 全自動化執行測試腳本，數十秒內直接揪出第一個壞掉的提交。

⚡ 深度專題：Git Worktree vs Git Stash

在真實團隊中，當遇到「緊急 Hotfix」或「需同時對比兩個分支」時，為什麼資深工程師更偏愛 Worktree？

比較面向 傳統 Git Stash 現代 Git Worktree
上下文切換方式 序列式：Stash ➜ 切換分支 ➜ 修復 ➜ 切回 ➜ Pop 平行式：直接在新目錄打開，原分支完全不動
編譯快取 / IDE 狀態 遭到刷洗（node_modules / build cache 常需重做） 完美保留（各目錄擁有獨立的檔案與快取）
還原時的衝突風險 較高（`stash pop` 經常發生衝突） 無（目錄實體隔離，互不干擾）
硬碟空間效益 低（單一工作區） 極高（共享同一個底層 .git 庫，非重複 clone）
