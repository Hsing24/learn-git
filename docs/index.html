🛠️ 現代 Git 指令演進：經典舊指令 vs. 現代更優實現

許多舊指令承擔過多職責或語意晦澀。現代 Git（2.23+）進行了大幅現代化升級，以下為業界最新推薦的寫法：

操作情境 傳統舊指令 現代更優替代指令 為什麼現代實現更好？
切換分支 git checkout <branch> git switch <branch> checkout 承擔切分支與復原檔案雙重職責，容易手滑覆蓋；switch 專門切分支，安全明確。
建立並切換新分支 git checkout -b <new> git switch -c <new> 語意更直觀對稱（-c 代表 create），降低認知負擔。
放棄工作區修改 git checkout -- <file> git restore <file> checkout -- 語法晦澀；restore 顧名思義就是還原，直覺不易打錯。
移出暫存區 (Unstage) git reset HEAD <file> git restore --staged <file> 不用搬出危險的 reset，restore --staged 精準描述取消暫存。
跨分支平行開發 (Hotfix) git stash ➜ 切換 ➜ pop git worktree add <dir> <branch> 實體目錄隔離，避免重編譯快取與 node_modules 失效，免除 pop 衝突風險。
新分支首次推送 git push -u origin <branch> push.autoSetupRemote true + git push 設定一次一勞永逸，任何新分支直接 git push，自動建立遠端同名分支。
微調修正歷史 Commit 手動 rebase -i 逐行改 squash git commit --fixup + --autosquash 自動將 fixup commit 移到目標下方自動合併，零手動編輯出錯風險。
拉取遠端最新代碼 git pull（預設 merge） git pull --rebase 避免產生雜亂無章的菱形交叉 Merge Commit，保持乾淨線性歷史。
二分法排查 Bug 手動一步步 good/bad git bisect run <test_script> 全自動化執行測試腳本，數十秒內直接揪出第一個壞掉的提交。
Git Hooks 團隊共享 手動複製腳本到 .git/hooks/ git config core.hooksPath .githooks .git/hooks 不受版本控制；core.hooksPath 或 Husky/Lefthook 讓全團隊自動共享守門員防線。
同檔局部暫存 (Atomic) 盲目全包 git add . git add -p <file> 依 Hunk 逐塊挑選（y/n/s），確保每個 Commit 具備單一職責，大幅提升 CR 品質。
停止追蹤機密檔案 刪除本地實體檔案再加 ignore git rm --cached <file> 只從 Git 索引除名，完整保全本地環境變數 (.env) 與開發資料。
線上回滾 Merge PR 危險覆蓋主線的 force push git revert -m 1 <hash> 向前推進產生反轉提交，清楚保留審計歷史，不破壞團隊他人進度。
重用衝突解法 (Rebase) 每次 rebase 手動解 10 次 rerere.enabled true Git 自動記憶衝突解決方案，後續相同衝突區塊 0 秒全自動填入！
精確代碼考古 大海撈針盲翻提交訊息 git log -S "<字串>" --oneline 鶴嘴鎬 (Pickaxe) 精準鎖定增減該字串次數的提交，比文字搜尋精準百倍。

⚡ 深度專題：Git Worktree vs Git Stash

在真實團隊中，當遇到「緊急 Hotfix」或「需同時對比兩個分支」時，為什麼資深工程師更偏愛 Worktree？

比較面向 傳統 Git Stash 現代 Git Worktree
上下文切換方式 序列式：Stash ➜ 切換分支 ➜ 修復 ➜ 切回 ➜ Pop 平行式：直接在新目錄打開，原分支完全不動
編譯快取 / IDE 狀態 遭到刷洗（node_modules / build cache 常需重做） 完美保留（各目錄擁有獨立的檔案與快取）
還原時的衝突風險 較高（`stash pop` 經常發生衝突） 無（目錄實體隔離，互不干擾）
硬碟空間效益 低（單一工作區） 極高（共享同一個底層 .git 庫，非重複 clone）

🛡️ 深度專題：Git Hooks 自動化守門員與工程化防線

如何透過 pre-commit 與 commit-msg 自動攔截 API Key 敏感金鑰、格式化代碼並規範團隊 Commit 訊息？

方案機制 運作方式與特點 優缺點評估
原生 .git/hooks 存放在本機 .git/hooks/ 私有目錄 缺點：不納入 Git 追蹤，每位工程師需手動配置，極易遺漏。
git config core.hooksPath 將 hooks 路徑指向專案版本控管目錄（如 .githooks/） 推薦（原生零依賴）：腳本隨 Git 庫同步版控，團隊一鍵生效。
Husky + lint-staged Node.js 生態標配，於 npm install 時自動掛載 hooks 推薦（前端生態）：只檢查暫存區檔案 (Staged)，大幅加速檢查。
Lefthook Go 撰寫的高效能多語言 Hook 管理工具 推薦（多語言專案）：平行極速執行，單一 YAML 設定檔乾淨俐落。

🚨 深度專題：線上生產救援 (Revert -m 1) 與 重複衝突終結者 (rerere)

面對複雜生產事故與跨分支 Rebase，資深工程師如何從容應對？

技術專題 痛點情境 最佳解決方案與原理
Revert Merge Commit PR 合併進 main 後引發線上事故，git revert 報錯缺少 -m git revert -m 1 <hash>：指定以 Parent 1 (主線) 為基準，精準反轉該 PR 的改動並保留審計紀錄。
Git rerere 在長壽分支上 Rebase，同一個衝突在 10 個 Commit 都要反覆手動解 git config rerere.enabled true：自動記憶解法，下次遇到完全相同的衝突區塊自動秒速套用！
.gitignore 失效救援 誤把 .env commit 進去，後續加進 .gitignore 依然緊追不捨 git rm --cached .env：已追蹤檔案不受 ignore 約束；透過 --cached 僅自索引除名，本地實體檔案完好無損。
